# Independent Google Drive recording uploader

This native Windows process runs separately from the WebView2 panel and the IPC agent. It uses the existing SQLite `drive_uploads` leases, immutable DPAPI credential revisions, reserved remote IDs and resumable Drive API uploads. No PIN, Apps Script token or browser OAuth token is used. It never deletes recordings.

Pass one absolute path to a native JSON configuration containing `Folder`, `IntegrationId`, `DriveFolderId` and `FromLocalDate`. The local recording folder must already exist. Configuration is local to the Windows user, not supplied by a website. Credentials must already be provisioned for that integration using the native OAuth flow. Files from the configured local day onwards are included, including future days.

Native renewal uses `HomeSecurityDriveSync.exe --authorize <absolute Desktop OAuth client JSON path> <absolute configuration path>`. It requests the existing `drive.file` scope, opens the system browser, uses PKCE/state validation, rotates the immutable DPAPI revision atomically and verifies destination access. It does not restart or recover the IPC agent's active commands. Initial access to an existing folder still requires native Picker provisioning; renewal does not silently broaden scope.

Normal discovery accepts `kamera-*.mp4` and `kamera-*.webm`, skips reparse points, waits for stable length/timestamp across scans and ten seconds since last modification, then acquires read sharing that excludes active writers. Files are streamed and hashed, never loaded whole into memory. Upload input is bounded at 16 GiB; chunks use 8 MiB of memory. A persisted matching path, size, MD5, integration and destination prevents another job after scanner restart. Two scanner instances are excluded by a per-user file lock. Queue leases also allow a maintenance worker to drain jobs concurrently without claiming the same job.

Optional `RecoveryFolder` is restricted to the existing HOME SECURITY WebView profile's `https_dominiksolorz.github.io_0.indexeddb.blob` directory. It recovers closed MP4 blobs identified by their `ftyp` header. Recovery filenames contain the **local file save time**, not a guaranteed recording start time. Original IndexedDB blobs are read, not renamed, deleted or modified. Existing recordings remain in the application's archive. Live recovery acceptance should additionally inspect media duration/audio/video with ffprobe.

`drive-sync-status.json` in the agent data directory reports scan state and video-job counts. Its timestamp may stay unchanged during a large upload. An independent five-second monitor writes `drive.sync` into the existing component-state table, so the read-only `system.snapshot` bridge exposes current job counts even during uploads. The panel displays this heartbeat; phone broadcasts contain only status, counts and timestamp, never native paths or credentials. `running` is not a delivery receipt. Only `succeeded`, after server size/MD5/parent/job-property validation, means the upload is confirmed.

The installed process and scheduled logon task are per-user. They require the PC to remain powered on and the Windows user session to be available. A Google testing-mode authorization may expire and need renewed consent; the uploader reports/blocks auth failures rather than claiming a successful copy. Folder privacy and available Drive storage must be checked separately. This is a cloud uploader, not an independent camera recorder.
