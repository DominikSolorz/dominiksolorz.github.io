# Public page structure

The homepage is a short product introduction with download, account entry and a few links. It must not contain full topic sections, embedded gallery/checklist, FAQ or chat. Keep the authenticated desktop homepage operational: real camera preview, real operator state and existing navigation commands.

Header, phone disclosure and footer must use page URLs rather than homepage section fragments. Common public layout is generated by `scripts/build-marketing.mjs`. Topic content and metadata live in `design/marketing/pages.json` and its HTML templates.

- `jak-dziala.html`: operation and device roles.
- `mozliwosci.html`: features and real use cases.
- `wymagania.html`: hardware, network, storage and Windows download.
- `przygotowanie.html`: configuration checklist.
- `stan-projektu.html`: availability and development limitations.
- `prezentacja.html`: illustrative panel preview, clearly labelled as concepts.
- `galeria.html`: full collection of UI concepts.
- `pobierz.html`: installation choices; Windows version comes from the release manifest.
- `blog/index.html` and article URLs: guides and first launch.
- `pomoc.html`: help choices and contact access.
- `kontakt.html`: dedicated contact form.
- `pytania.html`: FAQ and optional assistant; chat loads only after a click.
- Existing legal documents retain independent URLs and their current indexing policy.

Legacy public section fragments are mapped to the matching pages by `public-entry.js`. Account, PIN, native/PWA and OAuth entry routes must retain their original private gate. Topic pages must not import camera/account runtime.

Tests in `public-subpages.test.mjs` enforce this separation, functioning navigation targets, indexable canonical documents and legacy/private route behavior. Public hardening discovers these routes through the sitemap. Keep the public mirror builder and production URL verifier aligned when adding a page.
